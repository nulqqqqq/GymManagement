# Ревью GymManagement.Api

## Контекст
Ревью по запросу `/review`. Проект нужен для портфолио, это первый API-проект автора. Дальше в планах авторизация, тесты и новые фичи.
Режим наставника: код проекта не меняем. Ниже только замечания, без исправленного кода.
Номера пунктов используются командой `/check <N>`.

## Что сделано хорошо
- Слои разделены честно: Controller → I*Service → Service → DbContext. Контроллеры не трогают EF, наружу уходят DTO, а не сущности.
- FluentValidation, AutoMapper, Serilog и глобальный middleware для ошибок уже подключены. Для первого проекта это хорошая основа.
- Сортировка идёт по белому списку колонок, а не через динамическую строку.
- Есть XML-доки для Swagger и история миграций.

## Замечания

### Безопасность
1. **Секреты в git.** Где: `appsettings.json:10,18,23,26`. В git отслеживаются пароль БД, пароль приложения Gmail, ApiSecret Cloudinary и ключ JWT, а remote ведёт на GitHub. Секреты остаются в истории коммитов. Их нужно отозвать, просто удалить файл недостаточно. Для портфолио это ещё и красный флаг для ревьюера. Тема: User Secrets, переменные окружения, ротация секретов. **Высокий.**
2. **Мусор в репозитории.** В корне нет `.gitignore`, поэтому в git лежат `bin/` (даже `net10.0`), `logs/*.txt` и `.idea`. В логах есть email клиентов (см. п.24). Тема: `.gitignore` для .NET (`dotnet new gitignore`). **Высокий.**
3. **Почти все эндпоинты открыты.** `[Authorize]` стоит только на `StatsController.cs:7`. Любой анонимный пользователь может создавать и удалять клиентов, тренеров и тренировки (`ClientsController`, `TrainersController`, `WorkoutSessionsController`). Тема: авторизация в ASP.NET Core (fallback policy, роли, политики). **Высокий.**
4. **Login выдаёт токен админа кому угодно.** `AuthController.cs:18-23` не принимает логин и пароль и для любого запроса вызывает `CreateToken("admin_user","Admin")`. В итоге п.3 тоже ничего не защищает. Есть и вторая проблема: `TokenService.cs:9` не реализует `ITokenService` и не зарегистрирован в `Program.cs:41-46`. Поэтому DI не может создать `AuthController`, и каждый вызов login заканчивается 500. Модель `User` (`Models/User.cs`) не используется, у `UserName` нет уникального индекса. Тема: DI-контейнер (время жизни, регистрация), хэширование паролей (BCrypt), claims. **Высокий.**
5. **Детали исключения уходят клиенту.** `ExceptionMiddleware.cs:38`: `Detailed = exeption.Message` отдаёт наружу внутренние сообщения (SQL, имена таблиц, пути). Тема: ProblemDetails, `IExceptionHandler` (.NET 8+), разные ответы в Development и Production. **Средний.**
6. **HTML-инъекция в письме.** `EmailService.cs:27`: `clientName` вставляется в HTML без экранирования. Если передать `FirstName` вида `<a href=...>`, письмо со ссылкой на фишинг уйдёт от имени вашего Gmail. Тема: экранирование вывода, HTML encoding. **Средний.**
7. **Небезопасная загрузка фото.** `ClientsController.cs:141-148`: тип, размер и `null` файла не проверяются. Файл сначала загружается в Cloudinary, и только потом проверяется, есть ли клиент. Если клиента нет, `UpdateClientPhotoAsync` (`ClientService.cs:115-124`) молча ничего не делает, API отвечает 200, а файл остаётся в облаке без владельца. Старое фото не удаляется, хотя `PublicId` хранится и `DeletePhotoAsync` уже написан. Тема: валидация файлов, порядок операций, компенсирующие действия. **Средний.**

### Корректность и работа с данными
8. **Удалённые тренеры видны везде.** У `Trainer` нет глобального фильтра (`AppDbContext.cs:12-15`), а вручную `IsDeleted` нигде не проверяется. Поэтому удалённые тренеры попадают в список (`TrainerService.cs:24`) и их можно редактировать (`TrainerService.cs:60`). Их можно назначить клиенту (`ClientService.cs:107`) и записать к ним на тренировку (`WorkoutSessionService.cs:73`). `StatsService.cs:25` тоже считает их. Удалить тренера повторно можно, и это вернёт 204. Тема: Global Query Filters в EF Core. **Высокий.**
9. **При обновлении клиента Plan не проверяется.** В `UpdateClientValidator.cs` нет правила для `Plan`, поэтому PUT с `Plan="Gold"` или `""` проходит. Правило «Basic/Premium/Elite» нарушается. Тема: инварианты домена, enum вместо строк (см. п.21). **Высокий.**
10. **PUT может незаметно отвязать тренера.** `MappingProfile.cs:17` + `ClientService.cs:90-95`: если в `UpdateClientDto` нет `TrainerId`, AutoMapper запишет `null`, и тренер отвяжется. Если тренер не найден, сервис вернёт `false`, а контроллер ответит «Client not found» (`ClientsController.cs:109`), и сообщение вводит в заблуждение. Тема: семантика PUT и PATCH, явные результаты операций (Result pattern). **Средний.**
11. **Дубликат email даёт 500.** На `Email` есть уникальный индекс (`AppDbContext.cs:14`), но перед вставкой дубликаты не проверяются. Повторная регистрация падает с `DbUpdateException` и возвращает 500 вместо 409. Индекс учитывает и soft-deleted строки, поэтому удалённого клиента нельзя зарегистрировать заново. Тема: обработка `DbUpdateException`, фильтрованные (partial) индексы в PostgreSQL. **Средний.**
12. **TrainerId при создании клиента не проверяется.** `CreateClientDto.TrainerId` (`CreateClientDto.cs:12`) никто не проверяет. Несуществующий Id приводит к нарушению FK и 500. Кроме того, `Client.CreatedAt` нигде не заполняется (`ClientService.cs:69`). Тема: проверка ссылочной целостности на уровне сервиса, аудит полей (`SaveChanges` interceptor). **Средний.**
13. **DateTime и PostgreSQL.** Колонки имеют тип `timestamp with time zone`. Npgsql 6+ отказывается сохранять `DateTime` с `Kind=Unspecified`, а именно такой придёт из JSON без `Z` (`CreateWorkoutSessionDto.Date`). Результат: 500. Тема: `DateTime.Kind`, `DateTimeOffset`, UTC в Npgsql. **Средний.**
14. **Скрытый фильтр через Include.** `WorkoutSessionService.cs:50-51,62-63`: `Include(Client)` по обязательной связи вместе с фильтром `IsDeleted` на Client незаметно скрывает тренировки удалённых клиентов. Такая тренировка даже по Id отдаёт 404. При этом `WorkoutSessionResponseDto` не содержит Client и Trainer, так что Include вообще не нужны. Удаление клиента (`ClientService.cs:78-86`) не трогает его будущие тренировки. Тема: Include и query filters (предупреждение EF), каскадные правила для soft delete. **Средний.**
15. **Пагинация без ограничений.** `PaginationQueryDto.cs:5-6`: значения не валидируются. `PageSize=1000000` выгружает всю таблицу. `PageNumber=0` даёт отрицательный `Skip`, исключение и 500. Тема: валидация query-параметров, защита от тяжёлых запросов. **Средний.**
16. **Пагинация без сортировки.** `ClientService.cs:46-51`, `TrainerService.cs:42-46`, `WorkoutSessionService.cs:47-54`: если `SortColumn` не задан, `Skip/Take` выполняется без `OrderBy`. Порядок строк в PostgreSQL не гарантирован, и записи могут повторяться или пропадать между страницами. Общее количество (`totalCount`) не возвращается, поэтому фронт не сможет нарисовать пагинатор. Тема: детерминированная пагинация, `PagedResult<T>`. **Средний.**

### Обработка ошибок и контракт API
17. **Исключения вместо понятных ответов.** `WorkoutSessionService.cs:77` бросает `ArgumentException`, middleware превращает его в 500, хотя это ошибка клиента (400 или 404). В других местах «не найдено» передаётся через `bool`/`null`. В проекте два разных способа сигнализировать об ошибке. Тема: Result pattern или доменные исключения с маппингом на статус-коды. **Средний.**
18. **Разнобой в формате ответов.** Иногда возвращается чистый DTO, иногда `{message, Data}` (`ClientsController.cs:53`, `TrainersController.cs:44`). NotFound бывает строкой (`ClientsController.cs:109`) или объектом. `ProducesResponseType` обещает `ClientResponseDto`, а приходит обёртка, так что Swagger расходится с реальностью. `UpdateClient` возвращает `bool` в теле (`:112`). Тема: ProblemDetails, согласованный контракт REST API. **Средний.**
19. **Неправильный Location у тренера.** `TrainersController.cs:43`: `CreatedAtAction(nameof(GetTrainers), new { id })`. Эндпоинта `GET /trainers/{id}` нет, поэтому заголовок Location некорректен. `TrainerQueryDto` с фильтром `Specialization` создан, но не используется (`TrainersController.cs:25`). Тема: REST, статус 201 и заголовок Location. **Низкий.**
20. **Валидаторы create и update расходятся.** `UpdateTrainerValidator.cs` не проверяет Email и белый список специализаций, а `UpdateClientValidator` не проверяет Plan (п.9). Правила скопированы, и копии уже разошлись. Тема: переиспользование правил (`Include`, `SetValidator`, общий базовый валидатор). **Низкий.**

### Качество кода и читаемость
21. **Строки вместо enum.** `Plan`, `Status` и `Specialization` хранятся как строки (`Client.cs:10`, `WorkoutSession.cs:7`, `CreateTrainerValidator.cs:9-12`, `UpdateWorkoutSessionValidator.cs:10-13`). Списки допустимых значений дублируются, и опечатку компилятор не поймает. Это важно для новых фич, например абонементов и статусов. Тема: enum и value conversions в EF Core. **Средний.**
22. **Предупреждения nullable.** `Client.Plan` и `User.UserName` объявлены non-nullable без инициализации. `TrainerResponseDto.Specialization` (`:11`) тоже. `Trainer.PhoneNumber` объявлен как `string?`, но инициализируется `string.Empty` (`Trainer.cs:11`). Предупреждения компилятора игнорируются. Тема: Nullable Reference Types, `required`. **Низкий.**
23. **Дублирование и неточности.** Сортировка и пагинация скопированы в три сервиса. XML-доки не соответствуют поведению: «Permanently removes» при soft delete (`ClientsController.cs:77`), «integer identifier» при Guid (`:59`), «complete list» при пагинации (`:24`). Опечатки в ответах и сообщениях валидации: «succussfully», «not fount», «FistName», «hone number». Для портфолио это бросается в глаза. Тема: DRY, extension-методы для `IQueryable`. **Низкий.**
24. **Персональные данные в логах.** `ClientsController.cs:46,49` пишет email клиента в лог, а логи лежат в git (п.2). Тема: PII в логах, маскирование. **Низкий.**

### Архитектура и асинхронность
25. **Письмо отправляется прямо в запросе.** В `ClientsController.cs:48` контроллер оркеструет бизнес-процесс: сохраняет клиента, затем синхронно отправляет письмо через SMTP. Если SMTP упал, клиент уже сохранён, а API отвечает 500. Пользователь повторяет запрос и получает 500 из-за дубликата email (п.11). Ответ ещё и ждёт SMTP, а это секунды. Тема: фоновые задачи (`BackgroundService`, `Channel<T>`), паттерн Outbox, где должна жить оркестрация. **Высокий.**
26. **Нет CancellationToken.** Его нет ни в одном async-методе (контроллеры → сервисы → EF, SMTP, Cloudinary). Если клиент оборвал запрос, работа продолжается до конца. Тема: CancellationToken в ASP.NET Core. **Низкий.**
27. **Конфигурация через строки.** `EmailService.cs:20-37`, `PhotoService.cs:13-17`, `TokenService.cs:25-33`, `Program.cs:57-60` читают конфиг по строковым ключам и вызывают `int.Parse`/`!`. Ошибка в ключе проявится только во время выполнения. Тема: Options pattern (`IOptions<T>`, `ValidateOnStart`). **Средний.**
28. **Регистрации в Program.cs.** `AddValidatorsFromAssemblyContaining` вызывается дважды для одной и той же сборки (`Program.cs:39-40`). `AddAutoMapper(AppDomain...GetAssemblies())` сканирует все сборки. `FluentValidation.AspNetCore` 11.x устарел и не совпадает по версии с `DependencyInjectionExtensions` 12.x (`csproj:15-16`). Тема: авторегистрация в DI, зависимости NuGet. **Низкий.**

### Тестируемость
29. **Абстракция Cloudinary протекает.** `IPhotoService.cs:7-8` возвращает типы Cloudinary (`ImageUploadResult`), и контроллер разбирает `result.Error` и `SecureUrl`. Подменить провайдер или замокать его в тесте трудно. Тема: Dependency Inversion, собственные DTO на границе интеграции. **Средний.**
30. **Тестов нет.** Время берётся из `DateTime.UtcNow` прямо в коде (`CreateWorkoutSessionValidator.cs:14`), поэтому тест «нельзя записаться в прошлое» не сделать детерминированным. Тема: юнит-тесты (xUnit, Moq/NSubstitute), интеграционные тесты (`WebApplicationFactory`, Testcontainers для PostgreSQL), `TimeProvider`. **Средний.**

### Производительность
31. **Лишняя нагрузка в запросах.** Запросы на чтение идут без `AsNoTracking`. `StatsService.cs:27`: `Include` перед `Select` бесполезен, а 4 запроса выполняются последовательно. Лишние Include описаны в п.14. Тема: tracking и no-tracking, проекции (`ProjectTo`). **Низкий.**

### Бизнес-логика (на будущее)
32. **Нет проверки пересечений.** При создании тренировки не проверяется, занят ли тренер в это время. Тема: проверка пересечений интервалов, конкурентный доступ (оптимистичная блокировка). **Низкий.**
